## R33 — real mixed text provenance, bounded by matching method

The previous unsaved counts are appropriately withdrawn. A direct check of B001 confirms two distinct cases: node `347_0483-01` has a recorded `[Case Holding/Rule]` matching today's `substantive_holding`, while `349_0294-01` matches today's `clean_case_snippet(text,1200)` despite having a populated holding today. Thus the key observation—saved contexts mix holding-compatible and raw-text-fallback-compatible content—is supported and scientifically material.

However, `r33_holding_provenance_v2.py` classifies only the **first line** of each serialized item. Accordingly, 11,799 is a count of *first-line fallback compatibility under current rules*, not proof that the complete item came from that branch. The 670 NEITHER items also limit a global statement. The defensible node-level wording is: **no resolved node is classified as both HOLDING and FALLBACK by this first-line method**; “each case was always shown the same way” is too broad, because 121 nodes are HOLDING+NEITHER and 52 are FALLBACK+NEITHER. Post-run holding backfill is a plausible explanation, not a dated or byte-proven event. Please keep the manuscript's holding-coverage figures attributed to the later inspected graph state unless a run-time payload snapshot is found.

## R34 — distinct assembly profiles are visible; chronology is unproved

I independently checked discriminating full lines, not just the profiler output. In B001, a relation item for node `402_0001-01` is exactly today's holding truncated to **250** characters; in D001, a relation item for `305_0337-01` is exactly a **400**-character holding prefix. D001 and D002 each have a node line exactly `holding[:800]` while the current holding is longer. This supports the claim that recorded B and D contexts have different text-length profiles. All B and D rows remain labelled `_source_run=issue6_deployed`; none has a per-row date/time field. The evidence does **not** establish separate run dates, separate code files, or failure of a “single frozen run” in the chronological sense. A single code state with a category-specific branch or external processing difference also remains possible.

The exact **56 D rows / 99 B rows** profile counts are less secure than the direct examples: `r33_truncation_profile.py` searches for only the first 60 characters of `obs_head` in the entire context and uses the first occurrence. Repeated text or seed/relation reuse can attach that occurrence to a different item. A robust count should parse the full item directly with its case ID and observed text length, record only *discriminating* cases where the current holding exceeds the proposed limit, and classify ambiguous/nonmatching rows separately. Also, the addendum's “125 mid-text + 82 neither” explains only 207 of the 211 no-match items; no saved rule/output establishes the 82. Reconcile the remaining four and provide the rule if that breakdown is retained.
