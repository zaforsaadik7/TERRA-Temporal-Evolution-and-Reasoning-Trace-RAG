Exploratory AI-assisted author assessment
As an exploratory assessment, two project authors, neither legally trained nor licensed to practise law, reviewed 76 assigned response instances each with AI assistance. Author
1 drafted assessments and used AI for source finding, interpretation, checking and rewriting; Author 2 reviewed and amended AI-proposed ratings and rationales. Original
ratings were recorded before access to the other author’s ratings; reconciliation subsequently incorporated shared ratings and source-audit feedback. The sample includes
repeated questions and overlapping response instances, so the assignments are not 152 independent queries. These assessments are descriptive, not independent legal-expert
validation or population estimates.
Each author assessed 76 assigned rows. Non-refusal coverage includes substantive and mixed refusal/substantive responses. Supported-answer yield counts non-refusal rows
rated supported divided by all assigned rows. Contradicted among non-refusals divides contradicted rows by substantive-plus-mixed rows. These are descriptive proxies, not
verified legal-correctness measures. Supported ratings can reflect a correct central answer despite subsidiary errors. Uncertain ratings remain separate.

S3
Prospective controlled hybrid comparison
This fresh run is distinct from the canonical five-system evaluation and the earlier partial attempt. All 350 assigned queries (100 A, 100 B, 75 C, 75 D) completed. H used
native dense top-100 and Okapi BM25 top-100 candidates fused with reciprocal-rank constant 60; T used the same dense ranks, two seeds, depth zero/two nodes for EASY
and depth two/up to 40 nodes for HARD, with incoming/outgoing hub caps 75/25. Layer-1 stored document text was identical across sparse and dense indexing, while Layer-2
evidence fields came from one shared 20,000-node graph snapshot with 145,363 edges (145,310 citations and 53 overruling relations). This corrected snapshot is not an identity
claim about the historical 56-tag graph.
One query-only router selected EASY/HARD for both arms; this control did not exercise the legacy title-match or geometric-proximity helper and is not a replay of
the historical routing implementation. The arms shared the formatter, 6,000-token evidence budget and 7,000-token generator/verifier prompt ceiling; judges allowed 15,000
local input tokens, including the actual answer. Generator/verifier output caps were 4,096/512; judge caps were 1,024/4,096, with low GPT-OSS reasoning effort. The
same role-specific JSON schemas constrained router, verifier and judges in both arms, with plain-text generation. No malformed output was repaired. A negative verifier
decision produced a standardized refusal that both judges assessed. Generation temperature was zero, with hash-seeded arm order (seed 42); this does not establish provider
determinism.
Serving endpoints were Databricks Gemma 3 12B (router), Llama 3.3 70B (verifier/generator), Qwen3-Next 80B A3B and GPT-OSS 120B (judges). The archived packet
and raw returned identifiers bind this run; identifiers do not certify server weights or tokenizer equivalence. The recovered Gemma tokenizer retains its unresolved independent
upstream transport-receipt caveat. Provider-reported token usage was checked and settled for every request.
