## Codex findings I reproduced in the wrapper
1. **No finally-protected evidence (Codex #1).** `action_execute_diagnostic` has no try/finally. The Popen/readline loop (lines ~227-240) writes to the log and echoes to stdout; an exception in either (for example console encoding or disk write) leaves the child running unobserved and skips the exit-code file, metadata and post-hash. Two early `return 1` paths (pre-run SQLite hash mismatch, after the run directory is created) leave a directory with no metadata. The child's code is returned as the wrapper's code, and wrapper verification failure never changes it: a child exit 0 with a failed invariant still returns 0 (the invariants are only printed and stored).
2. **Pins not enforced (Codex #2).** `py_exe_sha`, versions and `diagnostic_sha` are measured and stored, never compared to pinned values. `DEFAULT_ONNX_CACHE` is hard-coded and not hashed by the wrapper; the snapshot is neither required nor compared. The default `UNKNOWN_OR_UNCONFIRMED_ENVIRONMENT` is accepted and passed to the child.
3. **Wrong report path (Codex #3).** The wrapper's `run_id` is its own; the child generates a different one and writes under its own `run_<id>` folder. `report_file_expected` (line ~283) therefore names a file that will not exist. The wrapper should inventory the child's run folder before and after and validate the single new report.
4. **Incomplete post-hash (Codex #4).** Post-run hashing covers only the SQLite file, two benchmarks and the summary, not the other ten store files, the diagnostic source, the interpreter, the six ONNX files or the historical script.
5. **Unsupported snapshot claims (Codex #5).** The docstring says read-only directory and active-writer detection; the code has neither, and compares the copy to the source manifest only after copying.

## Additional observations
- **A. The snapshot step opened the original SQLite with a client.** Line ~100 connects with `file:...?mode=ro`. Read-only SQLite on a WAL-mode file can need the -shm/-wal sidecars. Codex found the 11 store files unchanged, so no harm is shown, but this should be disclosed in the record as an original-store client opening (a plain read-only SQLite connection, not Chroma), since the user prohibited original-store client openings. For the snapshot already made, preserve it unchanged. Any future integrity check should use the snapshot copy, not the original.
- **B. Wrapper imports chromadb/onnxruntime itself** (lines ~197-201), before the child starts, in the same interpreter and outside any network guard. These imports open no store, but the measurement should run in a separate tiny child call or be documented as an in-wrapper import; either way the values must be compared to pins.
- **C. Authorship and permission evidence.** I agree with Codex that `codex-0043` was authored by Antigravity; preserve it with an attributed correction. In the user turns visible to me I see no user selection of the firewall option and no dated Step-1 authorization. The user said the offline-arrangement choice is still needed. Permission evidence for those should be cited by the user (date and wording) or marked unavailable.
- **D. A second-run guard.** One invocation is intended, but nothing stops a second invocation creating a new run folder. A simple exclusive "run-lock" file in the record directory, never deleted, would make the one-run rule checkable.
